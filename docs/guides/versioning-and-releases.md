# Kite 版本与发布规则

## 目的

Kite 的版本号用于告诉用户一次更新属于新功能还是修复，不表示提交数量、开发天数或工作完成比例。任何开发者或 AI 在判断版本时都必须遵守本规则，不能凭感觉跳号。

版本事实以两个位置为准：

- 最新已经发布的正式版本：GitHub 最新正式标签与 Release。
- 当前准备中的应用版本：`app/build.gradle` 的 `versionName` 和 `versionCode`。

## 四类独立版本

| 对象 | 用途 | 规则 |
| --- | --- | --- |
| `versionName` | 用户看到的 Kite 版本 | 使用 `主版本.功能版本.修复版本` |
| `versionCode` | Android 判断安装包新旧 | 每个对外分发的 APK 单调递增 |
| 资源商店 `revision` | 识别资源目录快照 | 独立递增，不触发 Kite 自动升版 |
| Rootfs、Agent 和其他资源版本 | 识别各自上游制品 | 保持上游版本与摘要，不占用 Kite 版本号 |

这些数字即使偶然相同，也不得互相推导或绑定。

## `versionName` 更新规则

Kite 在 `1.0.0` 之前使用 `0.Y.Z`：

| 本次发布相对上一正式版的最高影响 | 更新方法 | 示例 |
| --- | --- | --- |
| 新增用户可见能力、新 Agent、新安装或运行模式、新协议能力 | 功能版本 `Y + 1`，修复版本归零 | `0.3.21` → `0.4.0` |
| 只有 Bug 修复、兼容修复、性能优化和不改变能力的交互修正 | 修复版本 `Z + 1` | `0.4.0` → `0.4.1` |
| 只有文档、测试、构建辅助或内部整理，且不需要分发新 APK | 不发布新版本 | 保持原版本 |
| 破坏卡片、配置、会话、数据或安装升级兼容性 | `1.0.0` 前升功能版本并提供迁移说明；`1.0.0` 后升主版本 | `0.4.x` → `0.5.0`，或 `1.x` → `2.0.0` |

一次发布包含多种改动时，只采用影响最高的一类，只更新一次。例如同时包含多个修复和一个新功能，结果是功能版本，不按修改数量连续跳号。

## 版本周期

1. 以最新正式标签为比较起点，检查此后准备进入发布的全部改动。
2. 按最高影响确定一个目标版本。
3. 目标版本确定后，发布前计划内的新功能、复审和 Bug 修复都继续归入该版本，不逐提交再次升版。
4. 只有该版本正式发布后，下一轮新功能才升功能版本，纯修复才升修复版本。

例如，某轮发布目标设为 `0.4.0` 后，发布前继续完成计划内功能、复审和 Bug 修复，仍然属于 `0.4.0`。不能因为每完成一步就改成 `0.5.0`、`0.6.0`。

## Android `versionCode`

- `versionCode` 只负责比较安装包新旧，不展示给用户。
- 每个实际对外分发的 APK，包括 Alpha、Beta、RC 和正式版，都必须使用比此前所有已分发 APK 更大的值。
- 本地重复调试且没有对外分发时，可以继续使用当前值。
- 不把三段版本号编码进 `versionCode`，也不根据提交数生成它。

示例：

```text
假设此前最大 versionCode 是 41：
直接发布正式版：0.4.0 / versionCode 42
先发布候选版：0.4.0-rc.1 / versionCode 42
候选版后发布正式版：0.4.0 / versionCode 43
```

## 预发布名称

只有确实需要把未稳定安装包交给其他人测试时才使用预发布版本：

- `0.4.0-alpha.1`：功能还没有完成。
- `0.4.0-beta.1`：功能已经完成，正在扩大测试。
- `0.4.0-rc.1`：准备成为正式版，只接受阻断发布的问题。
- `0.4.0`：正式版本。

Git 标签在版本名前增加 `v`，例如 `v0.4.0`；应用中的 `versionName` 不增加 `v`。

## AI 执行约束

任何 AI 在回答“下一个版本是什么”或执行升版时必须：

1. 读取本规则。
2. 检查最新正式标签、当前分支、未提交改动和 `app/build.gradle`。
3. 比较最新正式标签之后准备发布的全部改动，不能只看最后一次提交。
4. 按最高影响给出唯一结果，不能用提交数、日期或主观工作量决定版本。
5. 只有获得用户明确授权后，才能同时修改 `versionName` 和 `versionCode`。
6. 构建 APK 后核对 APK 内的版本值；发布标签必须与 `versionName` 完全一致。
7. 未经明确授权，不得创建标签、推送或发布 GitHub Release。

提交消息中的 `feat`、`fix`、`perf` 可以作为判断线索，但不能代替真实业务影响。若提交类型与实际改动不一致，以真实用户影响和兼容边界为准。

## 发布前最低检查

- 发布范围已经确定，实验代码和不准备发布的内容已排除。
- `versionName`、`versionCode`、Git 标签和 Release 标题一致。
- 相关测试与正式构建通过。
- APK 签名、文件摘要和升级安装结果已验证。
- 真机冷启动没有崩溃或 ANR，目标功能结果已经确认。
- Release Notes 至少区分新增、改进、修复、兼容性变化和已知问题。
