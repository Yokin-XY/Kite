# Kite 主线稳定化执行母板

## 总目标

在不继续扩张 X11 和完整浏览器能力的前提下，把现有 Kite 主线规整成行为一致、
状态可信、生命周期可控、便于继续扩展的稳定产品。

本任务采用“会话分支、代码单主线”模式：不同 Codex 会话负责不同阶段，但所有
已验收成果都按顺序提交到本地 `main`。不为阶段建立并行 Git 开发分支。

## 固定原则

1. 不以拆文件数量代替职责转移。
2. 不新增平行状态源；继续使用现有 Store 和运行时事实源。
3. 用户动作必须立即进入处理中，最终状态必须由状态拥有者确认。
4. 普通状态变化只更新可见控件，不重建整页或运行显示面。
5. 页面生命周期、运行实例生命周期和底层进程生命周期必须分开。
6. 每个阶段必须有独立本地提交；禁止把多个阶段混成一个提交。
7. 每个阶段完成声明必须有测试、构建、静态检查或真机证据。

## 第二阶段：业务架构迁移

### 为什么进入第二阶段

D1-D5 已经建立导航、动作、状态投影和生命周期合同，但它们主要解决“行为先统一”。
现有代码仍有以下结构事实：

- `MainActivity` 仍约两万行，同时持有页面、动作、缓存、运行面和系统回调职责。
- `ResourcesFragment`、`ResourceSearchFragment`、`ResourceManageFragment`、
  `ResourceDetailFragment` 仍通过 Host 接口把真实渲染委托回 Activity。
- `ScreenRouter` 的公共合同依赖 `MainActivity.Screen`，导航模型仍属于具体页面壳。
- `CardRunActivity` 继承完整 `MainActivity`，单个运行窗口同时获得整套主应用职责。
- 资源相关渲染、动作和安装流程仍有数十个函数留在 Activity 内。

因此，D5 只能视为模块化样板完成，不能视为整个应用已经完成职责迁移。

### Kite 目标架构

采用“模块化单体 + 单向状态流 + 平台适配器”，先在现有 `:app` 内建立可靠包边界，
不立即进行多 Gradle 模块拆分，也不引入新的大型框架。

```text
App Shell
  MainActivity / CardRunActivity / AppNavigator / AppIntentRouter / AppGraph
        |
        v
Feature
  home / resources / run / terminal / web / settings
        |
        v
Application + Domain
  动作编排 / 业务规则 / 状态投影 / Store 合同
        |
        v
Platform
  PRoot / bridge / browser / file / toolchain / Android service
```

统一业务路径：

```text
用户或外部 Intent
-> Feature 提交 Action
-> Controller / UseCase 编排
-> 状态拥有者写入事实
-> Projector 生成 UiState
-> Screen 局部渲染
-> 导航、系统浏览器、权限窗口等一次性行为通过 Effect 交给 App Shell
```

依赖只能向下；Feature 之间不得直接操作彼此页面，只能使用稳定合同或向 App Shell 发 Effect。
页面不能复制长期事实，Controller 不能取代现有 Store，Platform 不能反向引用 Activity 或 View。

### 每个迁移任务的固定执行法

每个业务模块开始前都先建立“目的验收矩阵”：

1. 用户为什么进入这个模块，预期完成什么。
2. 哪个 Store 或服务拥有真实状态。
3. 点击后应立即显示什么承诺状态。
4. 后台如何确认成功、失败、继续等待和超时。
5. 页面离开、进后台、Activity 重建和内存压力分别如何处理。
6. 返回目标、外部窗口和运行显示面如何交接。
7. 哪些工作不得发生在绘制和绑定阶段。

发现现有逻辑不符合目的时：先用独立修复提交恢复业务合同，再用独立迁移提交转移职责。
禁止在机械搬迁中悄悄改变产品行为。

### T001 [P0] 架构基线与依赖护栏

问题证据：当前安全网能检查部分运行车道，但没有阻止新页面继续把渲染、动作和状态塞回
`MainActivity`，也没有约束 Feature、Domain、Platform 的依赖方向。

解法：记录现有业务入口、状态拥有者、显示面和生命周期矩阵；增加职责和依赖方向检查，
先锁住新增耦合，不要求一次清除全部历史债务。

验收标准：

- [x] 首页、资源、运行、终端、Web、设置六条业务链都有目的验收矩阵。
- [x] 建立允许依赖和禁止依赖清单，并由自动检查覆盖新增代码。
- [x] 建立 `MainActivity` 职责清单和迁移台账，能追踪字段、函数和 Host 接口归属。
- [x] 现有全量单测、Debug 构建和静态检查通过。

依赖：D1-D5 已完成。

### T002 [P1] 应用外壳与组合根

问题证据：导航合同依赖 `MainActivity.Screen`；Activity 自己创建大量 Store、桥接器、加载器和
Controller；系统 Intent、权限结果和页面渲染混在同一类中。

解法：建立独立 `AppDestination`、`AppNavigator`、`AppIntentRouter` 和轻量 `AppGraph`。
Activity 只装配依赖、托管根容器、转交 Android 生命周期与系统结果。

验收标准：

- [x] 导航模型不再引用 `MainActivity` 类型。
- [x] 外部 Intent 先被分类为应用动作或 Effect，再交给目标 Feature。
- [x] 进程级依赖由组合根创建，页面不再各自重复创建长期对象。
- [x] 不改变现有页面视觉、返回结果和浏览器认证协议。

依赖：T001。

### T003 [P1] 资源模块状态与控制边界

问题证据：资源事实已有 Store 和 Projector，但目录、详情、搜索、管理、安装向导仍共享 Activity
字段、缓存和请求序号，页面所有权不完整。

解法：建立 `ResourceFeatureContract`、Feature Controller/ViewModel 和依赖接口。继续复用
`KiteResourceInstallStore`、Registry、ManifestLoader 和现有 Projector，不复制资源事实。

验收标准：

- [x] 资源目录、详情、搜索、管理和安装向导使用同一 Feature 状态合同。
- [x] 加载、安装、卸载、取消、失败和待确认都有确定状态转换。
- [x] Controller 不持有 View，不直接导航，不重新定义安装事实。
- [x] 状态和动作合同测试通过。

依赖：T002。

### T004 [P2] 资源页面所有权迁移

问题证据：四个资源 Fragment 仍通过 Host 回调让 Activity 完成全部真实渲染。

解法：按“目录 -> 搜索 -> 详情 -> 管理 -> 安装向导”顺序迁移。Fragment/Screen 持有视图绑定，
Controller 提供 UiState 和 Action，Activity 只负责导航到资源 Destination。

验收标准：

- [x] 四个资源 Fragment 不再声明或调用 Activity 渲染 Host。
- [x] 资源相关缓存、绑定、请求序号和局部刷新离开 `MainActivity`。
- [x] 首页与资源各页面仍读取同一安装和运行事实。
- [x] 每迁移一个页面都有独立提交、Robolectric 回归和 OnePlus 8T 可见路径验证。
- [x] 返回位置、滚动位置、安装进度和失败重试不回归。

依赖：T003。

### T005 [P2] 首页卡片与配方编辑模块

问题证据：首页卡片渲染、卡片分组、配方表单、图标处理、步骤编辑和运行入口都位于
`MainActivity`，配置编辑与运行行为互相牵连。

解法：分为 `home` 与 `recipe-editor` 两个 Feature。首页只投影卡片和提交动作；编辑器拥有草稿、
校验和保存；真实配方仍由现有 Loader/Store 持有。

验收标准：

- [x] 首页不负责执行配方步骤，编辑器不直接管理运行实例。
- [x] 草稿、未保存返回、图标和步骤编辑状态归编辑模块所有。
- [x] 同一卡片从首页和编辑页启动时产生相同动作计划。
- [x] 首页结构变化与运行状态变化分开，普通状态变化不重建整个首页。

依赖：T002、T004。

### T006 [P2] 运行编排与执行引擎

问题证据：配方开始、步骤执行、进度处理、停止和残留进程判断仍大量依赖 Activity 方法，
执行核心与当前显示页面耦合。

解法：建立与 Android View 无关的 `RunOrchestrator`、`RecipeExecutor` 和停止协调器。继续让
`CardRunStore` 持有运行事实，Shell/Feature 只消费事件和 Effect。

验收标准：

- [x] shell、terminal、Web、X11 等步骤通过统一执行接口进入。
- [x] 开始、继续、停止、取消、失败和残留进程确认不依赖页面是否可见。
- [x] 同一 `instanceId` 不重复创建执行链，停止结果由执行层确认后落状态。
- [x] 执行层不引用 Activity、Fragment、View、Toast 或页面导航。

依赖：T005。

### T007 [P2] 运行窗口与显示面

问题证据：`CardRunActivity` 继承完整 `MainActivity`；终端、报告和 Web 显示面的创建、切换、
隐藏和恢复仍由主 Activity 统一维护大量字段。

解法：让 `CardRunActivity` 成为独立轻量外壳，由 `RunSurfaceHost` 组合 terminal、report、web
显示面；显示面只绑定指定 run instance，不拥有底层任务生命周期。

验收标准：

- [x] `CardRunActivity` 不再继承 `MainActivity`。
- [x] terminal、report、web 各自拥有显示生命周期和局部更新入口。
- [x] 页面离开只解绑显示面，用户停止才停止任务。
- [x] 外部浏览器回跳、终端恢复和报告更新仍回到正确实例。

依赖：T006。

### T008 [P2] 运行管理与运行时面板

问题证据：进程列表事实已经统一，但运行管理页面、运行时准入面板、权限门和部分停止确认仍
由 Activity 绘制和协调。

解法：建立 `runtime-management` Feature，消费 `TaskManagerStore`、运行快照和生命周期策略，
页面只提交刷新、打开、停止和回收意图。

验收标准：

- [x] 卡片、终端、服务和 PID 的归属在一个 UiState 中可追踪。
- [x] 停止中、已停止、失败和待确认按钮语义确定。
- [x] 内存压力不由页面直接杀进程，继续经过现有策略链。
- [x] 运行管理不通过整页重建等待后台状态追上。

依赖：T006、T007。

### T009 [P2] Web、浏览器与认证边界

问题证据：普通 WebView、系统浏览器认证桥、浏览器自动化和卡片 Web 显示面在 Activity 中
存在多组入口，认证协议正确性容易被页面迁移误伤。

解法：以 `web` Feature 管显示，以 browser platform adapter 管系统浏览器、loopback 和自动化。
强认证仍走官方系统浏览器；回跳作为 Effect/Intent 交给目标 run instance。

验收标准：

- [x] 普通 Web 显示、系统认证和自动化会话职责分开。
- [x] OAuth/loopback 参数原样桥接，不制造 Codex 或 Claude 专属特判。
- [x] 首次安装、覆盖安装、进程重建后的回跳都能路由到正确实例。
- [x] WebView 销毁、后台任务和认证会话具有不同生命周期。

依赖：T002、T007。

### T010 [P2] 设置、主题与首次启动

问题证据：设置绘制、主题保存、通知权限、文件权限、rootfs 准备和首次启动引导混在 Activity
生命周期中，恢复时容易重复弹层或重建页面。

解法：设置 Feature 管理显示状态；Onboarding Coordinator 管一次性步骤；Android 权限和设置页
跳转通过 Shell Effect 执行。

验收标准：

- [x] 设置状态、首次启动进度和运行时准备状态不互相覆盖。
- [x] 权限拒绝、返回、稍后继续和进程重建均有确定恢复点。
- [x] 主题变更只重绑必要页面，不重启后台任务。
- [x] 首次安装和已有用户升级路径分别通过真机验证。

依赖：T002。

### T011 [P3] 终端边界与应用壳清理

问题证据：终端已经拥有 Fragment 和动作注册表，但仍通过 `TerminalChromeHost` 控制 Activity
底栏；迁移完成后 Shell 中还会残留旧字段、Host 接口和兼容入口。

解法：终端通过通用 Surface Effect 请求沉浸/返回；按迁移台账删除旧委托、死字段和重复路径。

验收标准：

- [x] 终端 Feature 不依赖具体 Activity 类型。
- [x] `MainActivity` 只保留外壳、导航、系统回调和模块装配。
- [x] 不再存在 Feature Fragment 反向请求 Activity 渲染页面。
- [x] `MainActivity` 行数只作为防回涨指标，最终验收以职责清单清空为准。

依赖：T004-T010。

### T012 [P3] 依赖封口与发布验收

问题证据：包边界完成前直接拆 Gradle 模块会把循环依赖固化；架构迁移也可能引入启动、内存、
APK 体积和页面恢复回归。

解法：先消除反向依赖，再评估稳定合同是否值得拆成 `core`/`feature` Gradle 模块；执行完整
性能、生命周期、安装升级和业务链验收。

验收标准：

- [x] 自动检查阻止 Feature 反向依赖 Shell、Platform 依赖 UI、跨 Feature 直接调用页面。
- [x] 首页卡片、资源安装、运行窗口、终端、Web 登录、进程管理和设置关键链全部通过。
- [x] 冷启动、热返回、内存压力、APK 体积不劣于第二阶段基线。
- [x] OnePlus 8T 完成卸载重装、覆盖安装和长时间后台恢复验证。
- [x] 每个模块有明确所有者、入口、状态源、动作合同和生命周期合同。

依赖：T001-T011。

### T013 [P3] 实例窗口交互与通知信号封口

问题证据：运行窗口已经完成轻量壳与显示面拆分，但实例总览仍混入“完成步骤”全局动作，
等待步骤只按当前实例推进，无法拒绝来自旧代次、旧页面或错误步骤的迟到操作；Web 自有工具栏
的隐藏/显示也仍是瞬时切换。把“下一步”继续放在某个显示面，会重新制造固定位置冲突和页面
生命周期依赖。

解法：让 `RunOrchestrator` 用 `instanceId + generation + stepIndex + stepId` 校验精确步骤；
每个运行实例由进程级通知投影器消费 `CardRunStore` 事实，只有当前可继续步骤才显示“下一步”
通知动作。实例总览恢复停止、加号、返回三项，加号动画展开网页/终端选择。竖条单击仍只控制
当前显示面自己的工具栏，Web 工具栏补胶囊展开/收起动画。终端与 SH 工具栏本体不在本任务修改。

验收标准：

- [x] 旧代次、错误序号或错误步骤 ID 的“下一步”请求均被状态拥有者拒绝，不能推进其他步骤。
- [x] 通知按实例显示当前步骤、进度与结果；只有可继续状态才出现“下一步”，点击后立即进入处理中。
- [x] 通知不可用时不静默启动需要通知承载的运行；运行中到达人工门时只提示恢复通知能力。
- [x] 实例总览只有停止、加号、返回；加号动画展开“打开网页/新建终端”，不承载步骤继续。
- [x] Web 工具栏由竖条单击以胶囊动画展开/收起；双击总览和长按拖动保持既有语义。
- [x] 目标测试、全量检查、Debug 构建和 OnePlus 8T 关键路径通过。

依赖：T006、T007、T012。

### T014 [P3] 首页卡片通知生命周期封口

问题证据：现有进程级通知会把最终人工步骤继续投影成“下一步”，也会无条件保留完成、失败和
停止通知；通知只使用系统默认大文本样式，折叠、展开与横幅无法稳定表达“关闭/下一步”。
首页卡片自身也没有声明结束后是否保留结果通知，导致通知生命周期不能按卡片用途决定。

解法：在首页卡片 `launch` 配置中增加结束通知保留策略，默认结束即撤销。通知投影器只消费
`ownerKind=card` 的 `CardRunStore` 事实：运行中通知不可清除，非最终人工步骤显示精确“下一步”，
最终人工步骤及其他运行态显示真实“关闭”；保留的终态通知不再占用运行资源，可清除并通过既有
配方动作/运行编排链创建新代次。折叠、展开和横幅使用同一通知模型的自定义 `RemoteViews`，
系统仍负责通知外壳和弹出时机。用户清除终态通知只写通知展示抑制，不写入运行事实。

验收标准：

- [x] 最终人工步骤不产生完成步骤命令，只能通过“关闭”进入既有停止编排。
- [x] 中间人工步骤折叠态显示“下一步”，展开态显示“关闭/下一步”，动作携带精确代次和步骤身份。
- [x] 卡片默认结束即撤销通知；开启“保留结束通知”后，终态通知可清除并提供再次运行/重试。
- [x] 清除终态通知后，同一实例代次不会被普通 Store 信号或进程重启重新发布；新代次自动恢复通知。
- [x] 通知只覆盖首页卡片实例，不接管资源安装、安装向导或独立终端/Web 实例。
- [x] 目标单测、全量单测、Debug 构建和 OnePlus 8T 通知关键路径通过。

依赖：T013。

### T015 [P3] 通知权限与服务频道收口

问题证据：Kite 过去把系统通知能力显示成应用内可直接切换的开关，同时把首页卡片进度、容器
前台运行和未使用的设备 API 服务并列成通知类别。用户无法判断应当授权哪一类，厂商系统的横幅、
锁屏开关也无法从应用内直接控制；首次安装和旧版本升级后没有稳定进入首页卡片频道设置。

解法：遵循 Android 的应用通知权限与通知频道标准，不增加厂商或机型特判。首页卡片进度保留独立
高重要级频道；Android 强制要求的容器前台服务使用独立静默低重要级频道；删除无调用的设备 API
服务和旧频道。首次安装及既有安装升级一次性完成权限检查并打开首页卡片频道设置，设置页同样直接
进入该频道，不再用伪开关表示系统事实。

验收标准：

- [x] Android 13 及以上先检查通知运行时权限；Android 8 及以上使用独立通知频道。
- [x] 首次安装和旧版本升级只引导一次首页卡片频道设置，后续冷启动不重复跳转。
- [x] 首页卡片频道为高重要级；后台运行频道无声音、无振动、无角标且不用于卡片进度。
- [x] 未使用的设备 API 服务从 Manifest 和代码中删除；旧服务频道在升级后标记删除。
- [x] 设置页展示系统拥有的真实状态并进入具体频道，不伪装成应用可直接切换的开关。
- [x] 单测、全量构建、静态守卫和 OnePlus 8T 覆盖安装、冷启动、频道页面均通过。

依赖：T014。

### T016 [P3] 实例窗口重置与独立子窗口

问题证据：固定流程窗口与手动新建窗口共用显示面类型，导致“重新执行”“关闭”和终端会话复用的
所有权不清；同一实例也无法可靠表达多个同类型窗口。

解法：固定流程窗口由步骤拥有并允许重新执行；手动窗口使用稳定 `windowId` 和独立会话，只允许
单独关闭；停止实例时由既有运行编排统一回收全部子窗口。

验收标准：

- [x] 流程窗口重置不删除窗口，迟到回调不能覆盖新尝试。
- [x] 手动终端和网页拥有稳定窗口身份，可以创建多个同类型窗口。
- [x] 新建终端不复用父实例已有会话，关闭只结束目标会话。
- [x] 停止整个实例会回收固定流程窗口和手动子窗口。
- [x] Debug 构建和 OnePlus 8T 人工关键路径通过。

依赖：T013。

### T017 [P3] 一级导航与二级页层级封口

问题证据：资源详情、资源管理等二级页面仍显示一级底部导航，用户会把页面内部返回与全局 Tab
混为同一层级，也会让 Feature 页面继续依赖主导航的可见性特判。

解法：由 `DestinationContract` 声明是否显示一级导航；只有根目标拥有主导航，二级目标统一隐藏，
页面不再各自决定底栏可见性。

验收标准：

- [x] 配置、终端、资源和设置四个根目标显示一级导航。
- [x] 资源详情、资源管理及其他子目标不显示一级导航。
- [x] 返回仍经过统一导航合同，不改变页面业务事实。
- [x] 目标合同测试通过并完成独立本地提交。

依赖：T002、T016。

### T018 [P1-P3] 运行实例容器与进程闭环

问题证据：PRoot 原生遥测能够上报 owner、派生和退出事实，但 Android 端以裸 `traceePid` 保存生命周期，
PID 复用会继承旧终态；日志尾部读取和来源不健康时仍可参与破坏性动作。owner 关停只杀首批 PID，
已收集的 PGID 没有实际发送信号，新发现子进程只探测不补杀；owner 缺失也会被空集合误判为成功。
运行管理随后再用 owner、unit、终端和 PID 分数猜测归属，无法证明“停止实例”覆盖全部子、孙进程。

解法：先把底层事实收紧，再建立逻辑实例容器，不增加新的进程隔离层。遥测记录使用 session、PRoot
启动代次、宿主 PID 和 tracee PID 的复合身份；所有运行入口注入实例代次和叶子 owner；关停执行
“发现 -> TERM -> 复核 -> KILL -> 稳定静默确认”，来源不完整或 owner 缺失返回 Unknown，不冒充成功。
在此基础上由 `InstanceRuntimeContainer` 投影显式父子拓扑，运行管理只消费拓扑，实例关闭递归回收全部
叶子 owner；共享服务通过租约处理，不因单实例关闭而误杀其他实例。

验收标准：

- [ ] 同一 PID 在不同 telemetry session / PRoot 代次中不会继承旧 exit/signal 终态。
- [ ] 遥测读取单写者化；截断、跳段或来源不完整时，破坏性动作返回可解释的 Unknown。
- [x] 卡片、资源操作、流程终端和手动终端均带 `instanceId + generation + leaf owner` 身份。
- [ ] owner 关停会实际处理 PID 与 PGID，并反复发现、补杀新子孙，直到稳定静默或明确超时。
- [ ] 只有直接存活性复核通过后才写退出墓碑；owner 缺失不能单独证明已经停止。
- [ ] 实例拓扑可递归列出固定步骤、手动窗口、终端、Web、SH 和底层进程；共享租约不会被误回收。
- [ ] 运行管理不再用评分猜测进程归属，停止结果由同一拓扑和底层确认投影。
- [ ] 目标单测、全量单测、Debug 构建与人工真机多实例/子孙进程验收通过。

依赖：T006、T008、T016、T017。

### 第二阶段红线

1. 不以移动文件或减少行数冒充职责迁移。
2. 不进行 Compose、Navigation Component、Hilt 或多 Gradle 模块的同步大换血。
