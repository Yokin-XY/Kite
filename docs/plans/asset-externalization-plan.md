# 外部化实施方案（待确认）

> 目标：APK 从 243 MB → ~60 MB，不破坏 glibc Host 原生执行加速。

## 一、要移出 APK 的资产

| 资产 | 大小 | 放哪 | 怎么回来 |
|------|------|------|----------|
| Ubuntu rootfs 24.04 | 93 MB | GitCode/GitHub 镜像 | 首次启动时下载 + SHA-256 校验 |
| Node.js v26.4.0 linux-arm64 | 31 MB | 同上 | 首次启动时下载 |
| Python 3.14.6 aarch64 | 29 MB | 同上 | 首次启动时下载 |
| uv 0.11.25 aarch64 | 23 MB | 同上 | 首次启动时下载 |
| pnpm 11.9.0 | 4 MB | 同上 | 首次启动时下载 |
| **合计** | **180 MB** | | |

## 二、不移出 APK 的

| 资产 | 大小 | 原因 |
|------|------|------|
| glibc host launcher | 6 KB | Android/Bionic 编译，App 进程直接用 |
| glibc compat 库 | 67 KB | 同上 |
| kf-runner | ~100 KB | 进程管理基础设施 |
| App 本体 + UI | 39 MB | 就是 App |
| res + 资源清单 | 7 MB | 就是 App |
| **新 APK 总计** | **~47 MB** | |

## 三、下载机制设计

### 3.1 下载源（三层回退）

```
华为云镜像 → GitCode 镜像 → GitHub Releases
```

每个资产预计算 SHA-256，下载后校验。

### 3.2 下载时机

**方案 A：首次启动阻塞式**（推荐）
- App 打开 → 检测 rootfs 不存在 → 显示"准备环境"页面
- 显示：预计流量 XX MB、下载进度条（总进度 = 各文件进度加权和）
- 下载完成后自动解压 → 进入正常首页
- 预计首次耗时：3-5 分钟（WiFi）

**方案 B：按需下载**
- App 正常打开，终端能用（PRoot 有基础 Ubuntu）
- 装 Agent 时检测 Node.js 不存在 → 自动下载
- 更平滑但逻辑分散，出错点多

### 3.4 断点续传

- 用 Android 的 `DownloadManager`（系统级，自动断点续传）
- 下载到 `files/pending/` 目录
- 全部下载完成 + SHA-256 校验通过后原子移入正式目录

### 3.5 已有 rootfs 的用户（升级场景）

- 检测到 rootfs 已存在（从旧版 APK 提取的）→ 跳过下载
- 只下载缺失的增量文件（如新版 Node.js）

## 四、glibc Host 兼容性保障

关键约束：下载的 Node.js/Python 必须与当前 bundled 版本**完全相同**（官方构建）。

| 步骤 | 保证 |
|------|------|
| 下载 URL | 指向官方源（nodejs.org / python-build-standalone / astral.sh）或我们镜像的同一文件 |
| SHA-256 校验 | 与 APK 内置版本的哈希一致 |
| 安装位置 | `/workspace/.kf/toolchains/`（与现在相同） |
| wrapper | 仍然走 glibc host launcher（与现在相同） |
| 兼容层 | `libkite-glibc-compat.so` 保留在 APK（与现在相同） |

**唯一变化**：二进制从"APK assets 解压"变成"网络下载"——对 glibc host 透明。

## 六、风险与缓解

| 风险 | 缓解 |
|------|------|
| 首次下载失败 | 三层镜像回退 + 手动重试按钮 |
| 用户没网就打开 | 显示"需要网络准备环境"引导页，可稍后重试 |
| 下载的文件损坏 | SHA-256 校验失败自动重下 |
| glibc host 找不到 rootfs | 下载完成前不启动 glibc host preparer |
| 已有用户的升级 | 检测已有 rootfs 则跳过下载 |
