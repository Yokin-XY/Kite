# Kite 主题系统规范

## 目标

Kite 的主题系统首先是一套设计治理规则，其次才是设置页里的切换功能。

“统一入口”表示：

- 用户只在一个外观入口选择有效明暗、颜色方案和界面风格。
- 应用只有一个主题解析者，所有标准组件消费同一套语义。
- 新模块通过标准组件和语义 token 自动接入，不按页面名称增加主题分支。
- 特殊显示面有明确的适配边界，不强迫终端、网页、X11、图片和品牌内容完全同形。

“统一入口”不表示所有页面必须长得一样，也不表示所有视觉数值都允许用户切换。

本规范只确定分类、合同、扩展方式和验收规则，不确定最终品牌颜色，也不在只有一套稳定风格时承诺样式选择功能。

## 参考体系与 Kite 选择

成熟设计系统的共同做法是把原始值、语义、组件样式和业务页面分开：

- [Material 3](https://developer.android.com/develop/ui/compose/designsystems/material3) 把主题拆成颜色、字体和形状等子系统，由组件统一消费。
- [Fluent 2](https://fluent2.microsoft.design/design-tokens) 区分无上下文的全局 token 与带用途的语义别名 token。
- [Carbon](https://carbondesignsystem.com/elements/color/overview/) 要求不同主题保持 token 的角色不变，只替换角色对应的值。
- [Android Styles](https://developer.android.com/develop/ui/compose/styles/theming) 在主题子系统与组件之间增加组件样式层，并建议自定义设计系统让组件消费样式，而不是让业务页面直接拼视觉属性。
- [Android View 主题](https://developer.android.com/develop/ui/views/theming/themes) 明确把外观与界面结构、行为分开；主题提供语义资源，具体 View 样式消费这些资源。
- [Design Tokens Community Group 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/) 提供稳定的 token、分组和别名表达；Kite 当前不必引入跨工具 JSON，但命名与分层应当兼容这一思路。

Kite 采用下面的混合模型：

```text
原始值 Primitive
    ↓
语义 token Semantic
    ↓
组件配方 Component recipe
    ↓
Kite 标准组件
    ↓
功能模块

特殊内容：有效明暗 → 内容适配器 → 终端 / Web / X11 / 图片与品牌内容
```

功能模块不得越过组件配方直接根据 `styleKey` 选择样式，也不得为了一个页面的差异扩大全局主题协议。

## 核心概念

### 外观偏好

用户长期保存的选择，只包含：

- `colorMode`：跟随系统、亮色、暗色。
- `colorSchemeKey`：一套完整颜色方案，或能生成完整方案的受控种子。
- `stylePackKey`：一套标准组件的默认视觉配方。

用户偏好不保存页面作用域、组件实例颜色、临时间距或业务状态。

### 解析后的主题

主题解析者把用户偏好、Android 当前明暗状态和有效注册表解析为：

- 有效明暗。
- 语义颜色。
- 固定设计基础。
- 组件配方。
- 特殊内容的适配策略。

页面只能读取解析后的结果，不能读取主题 SharedPreferences、重新判断系统明暗或自行组合一套主题。

### token 化不等于可切换

token 的作用是给设计决定命名并消除散落硬编码。一个值进入 token 系统，不代表它必须成为用户主题选项。

例如基础页面边距、最小触控尺寸和正文层级需要 token 化以保持一致，但它们属于固定设计基础，不跟随颜色方案或界面风格切换。

## 分类规则

### 一、颜色主题：允许切换具体值，语义保持不变

适合进入颜色主题的内容：

| 语义组 | 典型用途 |
| --- | --- |
| 背景与表面 | 页面背景、普通表面、抬升表面、遮罩层 |
| 文字与图标 | 主文字、次文字、弱文字、反色文字、禁用内容 |
| 边界 | 普通描边、强调描边、分隔线、焦点环 |
| 操作 | 主操作、次操作、选中态、按下态、禁用态 |
| 反馈 | 成功、警告、危险、信息及其弱背景和边界 |
| 系统外壳 | 状态栏、导航栏、窗口背景、启动过渡背景 |

颜色主题可以改变这些角色的实际颜色，但不能改变角色的含义。例如危险状态在暗色下可以使用另一档红色，但不能映射成成功色。

颜色方案必须一次产生完整的前景/背景配对和交互状态，不能只保存一个强调色和一个背景色后让各页面自行混色。若以后允许用户选择任意种子色，应由中央生成器产生完整亮色/暗色语义方案并通过对比度门禁。

### 二、界面风格：只改变标准组件的视觉配方

适合进入 `stylePack` 的内容：

- 卡片使用填充、描边还是轻抬升。
- 按钮、输入框、标签和选择项的标准视觉变体。
- 圆角尺度及其在卡片、控件、标签、图标容器中的语义映射。
- 描边粗细、阴影/色调抬升策略。
- 图标容器、对话框、顶栏和底部导航的表面处理。
- 组件内部在安全范围内的留白，但不得改变页面网格、信息密度和最小触控尺寸。

每套风格都必须提供完整的组件配方；功能页不能写“如果是某风格就使用某圆角”。同一风格可以让卡片与按钮不同形，但这种差异由组件配方决定，不由页面决定。

只有一种稳定风格时，设置页不显示没有实际选择意义的风格选择器。第二套风格必须经过全量组件证明后，才能成为用户可见选项。

### 三、固定设计基础：需要统一，但不随主题切换

以下内容必须标准化，却原则上不属于主题选择：

- 页面基础边距、间距网格和内容最大宽度。
- 字体语义层级、基准字号与行高；系统字体缩放继续由 Android/无障碍设置控制。
- 不小于 48dp 的主要触控目标及其他可访问性底线。
- 导航位置、页面结构、功能排列、信息层级和操作顺序。
- 组件功能、状态机、加载/成功/失败语义和内容文案。
- 屏幕尺寸、横竖屏和大屏适配规则。
- 减少动画等无障碍偏好；即使以后可配置，也应是独立显示偏好，不与颜色或风格包捆绑。

界面风格不得借改变圆角或卡片形式之名，重排功能、隐藏信息、缩小触控面积或改变业务行为。

### 四、独立内容外观：只做边界适配，不做全局染色

| 内容 | 跟随应用的部分 | 保持独立的部分 |
| --- | --- | --- |
| 终端 | 页面外壳、输入区、操作面板、有效明暗 | ANSI 语义色板、进程输出、光标/选择区专用规则 |
| 代码与日志 | 容器、标题、工具栏、普通说明 | 原始日志、语法色板、ANSI 转义语义 |
| WebView | Kite 导航外壳；向支持的网页传递有效明暗 | 网页自身 CSS、品牌和第三方内容，不强制反色 |
| X11 | Kite 外壳、加载/错误提示 | 原生 X11 画面和远端应用内容 |
| 图片与资源海报 | 容器、占位和边界 | 图片像素、资源封面、品牌 Logo |
| 图表/分类色 | 外壳、标签文字、背景适配 | 数据系列之间的稳定区分及其专用可访问性色板 |

特殊内容通过显式 `ContentAppearanceAdapter` 接收有效明暗和必要语义，不进入普通组件风格包。不能因为它位于某个页面，就为整个页面增加主题作用域。

## 统一入口的产品结构

设置中的“外观”保持一个入口，内部按用户能理解的层级排列：

1. 显示模式：跟随系统、亮色、暗色。
2. 颜色方案：完整的品牌/个性化色组；不展示底层 token。
3. 界面风格：只有存在至少两套已验收风格时才显示。
4. 预览与恢复默认：以后需要时增加，不能先于完整方案和回滚能力。

终端等特殊工具可以在自己的设置页提供“跟随应用/独立亮色/独立暗色”，但“跟随应用”必须消费同一个有效明暗，不能再次读取系统状态。

统一的是入口和解释权，不是把所有特殊内容偏好塞进同一个 `SettingsSnapshot`。

## token 和组件配方命名

### 原始值

原始值只允许存在于主题定义层，例如：

```text
palette.neutral.0
palette.neutral.90
palette.brand.60
dimension.radius.3
dimension.space.4
```

业务页面不得直接消费原始调色板或数值档位。

### 语义 token

语义名称表达用途，不表达颜色名称或页面名称，例如：

```text
color.background.page
color.surface.default
color.surface.raised
color.text.primary
color.text.secondary
color.border.subtle
color.action.primary
color.action.onPrimary
color.status.danger
color.status.onDanger
shape.container.medium
elevation.surface.raised
```

禁止使用 `homeBlue`、`settingsCardRadius`、`terminalPageBackground` 这类把功能页写入全局主题的名称。

### 组件配方

组件配方按组件家族和语义变体命名：

```text
component.card.standard
component.card.interactive
component.button.primary
component.button.secondary
component.button.danger
component.input.standard
component.chip.selected
component.navigation.bottom
component.dialog.standard
```

组件配方可以引用语义颜色、形状和固定基础，但不得引用业务 Store、页面状态或功能模块类型。

## Kite 标准组件目录

新模块优先从下列组件家族组合界面。这里是规划合同名，不要求一次性创建同名 Kotlin 类：

| 家族 | 组件 |
| --- | --- |
| 页面外壳 | `KitePage`、`KiteTopBar`、`KiteBottomNavigation` |
| 结构 | `KiteSection`、`KiteDivider`、`KiteStatusBlock` |
| 操作 | `KiteButton`、`KiteIconButton`、`KiteActionRow` |
| 输入与选择 | `KiteInput`、`KiteChoiceRow`、`KiteSwitchRow`、`KiteChip` |
| 内容 | `KiteCard`、`KiteListRow`、`KiteBadge`、`KiteIconTile` |
| 覆盖层 | `KiteDialog`、`KiteSheet`、`KitePopup` |
| 运行外壳 | `KiteRunChrome`、`KiteRunStatus`；内部终端/Web/X11 继续由专用绑定拥有 |

首页、资源和设置现有工厂中的重复状态块、卡片、动作按钮和圆角容器，应逐步收敛到这些组件家族；不要求为了规划一次性重写所有命令式 View。

## 当前落地状态

- `ThemeProtocol.kt` 已建立 Android-free 的 `ThemeCommand`、`ThemeSelection`、`ThemeCatalog` 和 `ThemeEnvironment`；`KiteTheme` 统一归一化、回退和解析。
- `ThemeEnvironmentGateway` 由 `KFApplication` 提供，主要页面通过统一环境取得有效明暗和语义颜色，不再存在页面级 `ThemeScope`。
- `AndroidSettingsGateway` 是旧裸颜色键的唯一迁移入口；新写入使用颜色选择类型、完整方案键、风格包键和模式。
- 首页和设置已分别消费 `ThemeFoundations` 与 `ThemeComponentRecipes`，证明固定基础和可换组件配方能够独立接入。
- 当前目录只有一套 `standard` 颜色方案和一套 `standard` 风格包，因此设置页只显示真实可操作的明暗模式，不显示临时调色板或单选项风格入口。
- `UiKit` 目前主要提供 `dp`、圆角背景、图标按钮和顶栏等绘制工具，还不是包含语义变体、状态和完整风格配方的设计组件层。
- 资源、编辑器、运行管理和报告已消费统一语义颜色，但重复卡片、按钮、状态块和容器仍需在后续任务中逐步迁移到标准组件；这不影响本轮中间协议成立。
- 编辑器、运行报告、运行窗口和运行状态外壳虽然已经消费部分 `ThemeTokens`，仍包含较多局部颜色、圆角、间距和层级数值。不能把这些数值全部机械搬进全局主题；应先按本规范判断它们属于语义颜色、组件配方、固定基础还是独立内容。
- 终端、WebView 和 X11 已经由不同显示绑定拥有真实内容和生命周期，适合保持“外壳统一、内容适配”的边界，不应抽象成普通页面风格。

因此下一轮重点不是继续扩大 `KiteTheme` 字段，而是先建立少量真实标准组件，再从重复最明显的界面逐步迁移。迁移必须保留现有状态拥有者、局部更新和显示面生命周期。

## 新模块接入标准

### 接入判断顺序

1. 先判断新增内容是普通应用 UI，还是终端、网页、X11、图片、图表等独立内容。
2. 普通 UI 优先组合现有 Kite 标准组件，不直接创建主题分支。
3. 缺少的只是颜色角色时，先确认现有语义 token 是否已经表达该用途。
4. 缺少的是可复用视觉结构时，增加组件变体或组件配方。
5. 只有跨多个组件稳定复用、且无法用现有语义表达的决定，才新增基础 token。
6. 单次业务展示保持在功能模块内；它可以消费语义颜色，但不能反向扩大全局主题合同。
7. 特殊内容使用专用适配器，只同步允许同步的环境信息。

### 新模块提交检查表

- [ ] 没有读取 `kite_theme` 或自行判断系统明暗。
- [ ] 没有根据 `styleKey`、颜色名称或页面名称写条件分支。
- [ ] 普通文字、表面、边界和状态使用语义 token。
- [ ] 操作控件来自标准组件或已登记的通用组件变体。
- [ ] 页面边距、字体层级和触控目标使用固定设计基础，不随主题包变化。
- [ ] 终端、Web、X11、图片、品牌和数据色已经明确独立边界。
- [ ] 亮色、暗色、至少一套证明风格下内容完整、含义不变、操作可达。
- [ ] 主题变化不修改运行、资源、安装、会话或页面业务状态。
- [ ] 可见更新只重绑必要外观，不重建终端、WebView、X11 或运行实例。

### 新 token 准入规则

新增 token 必须至少满足一项：

- 表达当前体系缺失且长期稳定的语义角色。
- 被两个以上组件家族复用。
- 是达到对比度、平台适配或无障碍要求所必需的状态。

不能因为“当前页面需要一个 17dp 圆角”就新增全局 token。若没有合适 token，先判断它是现有组件配方缺口、业务内容局部值，还是设计本身尚未形成重复规则。

## 局部差异和覆盖规则

默认情况下不存在页面级 `ThemeScope`。

局部差异按以下顺序解决：

1. 使用同一组件的语义变体，例如普通卡片、交互卡片、危险按钮。
2. 使用表面层级，例如基础表面、抬升表面、遮罩层；层级按用途命名，不按页面命名。
3. 使用特殊内容适配器，例如终端色板或 Web 内容明暗桥接。
4. 只有某种完整显示环境具备跨页面、跨组件且长期稳定的不同设计语言时，才提出新的子主题；必须有独立规范和全组件验收，不能由单个功能页直接添加。

## 当前默认主题实现的处理结论

上一轮实现不是白做，但要把它视为主题管线的技术底座，而不是最终分类模型。

### 可以保留

- `ThemeEnvironmentGateway` 作为应用级唯一读取入口。
- `SYSTEM/LIGHT/DARK` 模式及 Android 有效明暗解析。
- 页面不再直接读取主题 SharedPreferences 的迁移结果。
- `ThemeTokens` 中已经具有明确用途的背景、文字、边界、操作和状态角色。
- Activity 系统栏与应用有效明暗对齐。
- 终端“跟随应用”与终端 ANSI 色板独立的边界。
- 设置持有主题模式和未来风格注册键的方向。
- 已建立的单元测试、构建门和真机明暗证据。

### 当前已完成调整

- 删除把 `HOME/RESOURCE/SETTINGS/EDITOR/RUN/TERMINAL` 当成长期扩展方式的页面级 `ThemeScope`；普通页面回到同一环境。
- 把 `ThemeComponentStyle` 拆成固定设计基础与按组件家族组织的配方，不能让一份全局对象同时代表页面网格和所有组件。
- `ThemeSpacing` 中的页面边距、段落间距等归入固定基础，不随 `stylePack` 切换。
- 将 `themeColor/backgroundColor` 的独立原始值升级为完整 `colorScheme` 或受控种子生成器，中央保证前景/背景配对和对比度。
- 首页和设置已成为第一批组件配方消费者；资源、编辑器和运行显示面的重复组件留在阶段 C 继续迁移。
- 当前只有 `standard` 时隐藏无意义的风格选择器；保留注册能力，但不制造“可以选择”却只有一个选项的入口。

### 不应推倒重做

不回退统一 Gateway、系统模式、语义颜色接线和终端边界。后续调整应沿现有单一入口收窄协议，把页面作用域改成组件配方和内容适配器；不得重新恢复分散 SharedPreferences 或页面自行解析主题。

## 分阶段落地

### 阶段 A：冻结标准（已完成）

- 在本规范确认前不新增第二套用户可见风格。
- 把当前 `standard` 定义为兼容现状的过渡实现，不作为最终品牌视觉承诺。
- 为禁止页面作用域、原始主题读取和 `styleKey` 页面分支建立静态检查目标。

### 阶段 B：重整合同，不改变视觉（已完成）

- 保留 `ThemeEnvironmentGateway` 和有效明暗解析。
- 建立 `ColorScheme`、固定 `DesignFoundations`、`ComponentRecipes`、`ContentAppearancePolicy` 的边界。
- 移除页面名称驱动的主题覆盖；现有界面保持原有排列和操作。

### 阶段 C：建立标准组件（首页与设置样板已完成，其余渐进迁移）

- 先迁移首页、设置、资源共用的卡片、按钮、状态块、选择行和顶栏。
- 再迁移编辑器、运行管理、运行报告等重复容器。
- 每次迁移只替换视觉构建方式，不改变状态拥有者、动作链和刷新方式。

### 阶段 D：特殊内容适配

- 终端外壳跟随应用，ANSI 色板继续由终端模块拥有。
- WebView 只传递支持的明暗偏好，不强制修改第三方网页。
- X11、图片、品牌和资源封面保持内容独立。

### 阶段 E：证明可扩展性

- 增加一套仅用于测试的明显差异风格，覆盖卡片、按钮、输入、标签、导航和对话框。
- 验证新增风格只需注册组件配方，业务页面无需改代码。
- 证明风格不会改变布局、内容、触控目标、会话或运行状态后，才讨论第二套正式用户风格。

### 阶段 F：用户入口与真机验收

- 完整验证跟随系统、亮色、暗色和每套正式颜色方案。
- 有两套以上已验收风格时才开放风格选择。
- 在 OnePlus 8T 检查所有标准组件、系统栏、终端外壳、Web 外壳和运行窗口。

## 验收门

主题系统达到可长期扩展，至少满足：

- 生产页面直接读取主题 SharedPreferences 为 0。
- 业务页面按 `styleKey` 或颜色名称写主题分支为 0。
- 页面名称型主题作用域为 0。
- 标准 UI 的原始主题颜色只存在于主题定义层；内容适配器和真实资产例外必须有明确边界。
- 普通文字与背景对比度不低于 4.5:1；必要图形、控件边界和大文字遵守适用的至少 3:1 门槛，平台要求更高时采用更高标准。
- 切换颜色方案只改变语义值；切换风格包只改变组件视觉配方。
- 导航、功能排列、文案、触控目标和状态机在所有主题下保持一致。
- 新模块按检查表接入，不修改主题解析者即可得到完整默认外观。
- 主题变化不重建终端、WebView、X11 或运行实例，不触发资源、安装和运行事实重查。
- 单元测试、Lint、架构/压力门和 OnePlus 8T 明暗真机验收通过。

## 已确定与暂不确定

已经确定：

- 单一外观入口和单一主题解析者。
- 颜色、组件风格、固定设计基础和独立内容四类边界。
- 普通功能页不拥有主题作用域。
- 新模块通过标准组件与语义 token 接入。
- token 化不等于用户可切换。
- 特殊内容通过适配器有限跟随。

暂不在本规范决定：

- 最终品牌主色和正式颜色方案数量。
- 第二套正式风格的具体视觉方向。
- 是否允许系统动态颜色或用户任意种子色。
- 是否在未来提供字体家族、信息密度或动画偏好；这些即使提供，也不默认并入主题包。
