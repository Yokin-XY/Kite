# Kite X11 1080P 与超级操作模式决策记录

## ADR-001 1080P 按标准横向 `1920x1080` 处理

- 日期：2026-07-02
- 决策：用户说“固定分辨率为1080P”，本任务按标准 1080P 桌面尺寸 `1920x1080` 实现。
- 理由：当前 X11 已是横向固定桌面 `1280x720`；用户此前也多次把 X11 类比为手机远控桌面，标准 1080P 在桌面语境中通常指 `1920x1080`。
- 影响：`X11ViewportPlan`、相关测试、`sendWindowChange(...)` 的逻辑桌面尺寸都应改为 `1920x1080`。
- 回滚：如果后续用户明确说“1080P”指竖向 `1080x1920` 或只指短边 1080，则新增方向预设，而不是推翻固定桌面模型。

## ADR-002 “超级操作模式”作为用户口径，不臆造官方单一功能名

- 日期：2026-07-02
- 决策：文档中保留“超级操作模式”作为用户口径，同时把公开资料中真实出现的能力拆成触摸模式、指针模式、自定义键盘、长按交互、虚拟键盘、双指缩放等。
- 理由：目前公开搜索没有稳定找到官方页面直接命名为“超级操作模式”；强行当成一个官方功能名会误导实现。
- 影响：T1 文档和后续 T3 实现按能力拆分，不按一个模糊菜单名实现。

## ADR-003 适配目标是原生内嵌 X11 surface，不引入远程桌面中转

- 日期：2026-07-02
- 决策：继续在 `CardRunSurface.X11` 和 `LorieView` 里适配，不引入 VNC、noVNC、websockify 或独立远程桌面页面。
- 理由：当前产品方向是卡片实例里的原生 X11 surface；之前记忆和项目边界都要求保留 card -> instance -> surface 所有权。
- 影响：代码改动优先落在 `LorieView`、`X11ViewportPlan` 和对应测试，不改 CardRun 运行状态所有权。

## ADR-004 先做视口相机，再谈菜单工具

- 日期：2026-07-02
- 决策：T3 优先实现双指缩放、双指拖动画面和输入映射；不先做工具菜单或复杂浮层。
- 理由：用户此前明确强调“不是做菜单”，核心是手指缩放和挪动效果；本次主线也是直接适配 X11，而不是设计完整远控工具栏。
- 影响：本轮不新增 X11 工具栏，不新增菜单入口，避免 UI 范围蔓延。

## ADR-005 初始视口采用主轴铺满，不采用完整包含

- 日期：2026-07-02
- 决策：X11 初始显示按手机方向采用主轴铺满：横屏宽度铺满，竖屏高度铺满；横屏高度溢出时默认隐藏上方溢出区域。
- 理由：用户指出上一版完整包含会让 1080P 桌面在手机上变成小框悬浮，且上方白条未适配。远控体验应优先让一个主轴铺满屏幕，再通过视口相机平移查看被裁切区域。
- 影响：`X11ViewportPlan.fitLandscapeDesktop(...)` 的语义从 contain 改为主轴 cover；对应测试锁定竖屏高度铺满和横屏宽度铺满。

## ADR-006 单指移动优先拖动画面，轻点才发送远端点击

- 日期：2026-07-02
- 决策：`LorieView` 单指输入改成阈值模型：按下不立刻发送远端鼠标；手指移动超过系统 touch slop 且当前相机可平移时，单指拖动画面；抬起且未形成拖动时，才发送一次远端点击。
- 理由：如果按下立即发鼠标，单指拖动画面必然误触远端内容。用户要求非内容/边缘过渡区域能单指挪动，小框内容区仍能点击，因此需要把“轻点”和“拖动画面”区分开。
- 影响：单指轻点仍可点击远端；缩放后或主轴铺满裁切后，单指移动可以继续平移视口。

## ADR-007 X11 服务启动失败必须回传错误，不直接崩服务进程

- 日期：2026-07-02
- 决策：`KiteX11ServerService` 捕获 Java/Kotlin 启动失败并通过 Binder 暴露启动错误；`KiteX11SurfaceServer` 绑定后读取错误并让 CardRun/open-desktop 进入可解释失败。
- 理由：用户指出实例容易闪退。当前服务内 `require/check` 失败会打断 `:x11` 服务生命周期，表现为实例或 Surface 断开；更合理的是让状态拥有者得到失败原因。
- 影响：不隐藏异常，也不靠重建页面兜底；失败会变成可记录、可返回、可显示的错误。

## ADR-008 缩放/拖动只改变本地视口相机，不改变 X11 桌面尺寸

- 日期：2026-07-02
- 决策：`LorieView` 的双指缩放和单指拖动画面只更新 Android 端 renderer viewport 与输入映射；`sendWindowChange(...)` 只用于首次或真实桌面尺寸/刷新率变化通知。
- 理由：用户明确要求缩放不影响底层分辨率变化；远控式缩放应像观察相机一样工作。当前手势 MOVE 每次都发送 `1920x1080` 窗口变化，会在高频触摸路径上制造不必要的 native/X11 压力。
- 影响：固定桌面继续是 `1920x1080`；手势缩放/平移不会改变 X11 应用看到的桌面尺寸；崩溃排查先收敛到减少窗口变化通知压力，再做真机多次缩放验证。

## ADR-009 采用 Termux:X11 native source-rect 机制，放弃负坐标目标矩形

- 日期：2026-07-02
- 决策：`setViewport(...)` 只用于 Android surface 内的非负目标绘制矩形；铺满、缩放和输入映射转为使用 native `setRendererZoom(...)` 与 `setRendererViewport(...)` 回传的 source rect。
- 理由：用户截图证明负坐标目标矩形模型在真机上会把内容放到画布外，并使纵向轴锁在上方。Termux:X11 upstream 与本地 `libXlorie.so` 均表明 native 已有 renderer zoom/source-rect 回传机制，Java 不应另造一个负目标矩形相机。
- 影响：初始铺满通过 renderer zoom 计算；缩放不改变 X11 桌面尺寸；单指拖动画面需要通过 native source rect 和鼠标边缘带驱动 panning，而不是改 `sendWindowChange(...)`。

## ADR-010 文件管理资源初始视口采用自动适配，不再初始裁切放大

- 日期：2026-07-02
- 决策：固定 X11 桌面继续是 `1920x1080`，但手机端初始显示改为完整自动适配；只有用户双指放大后才进入 source-rect 裁切和平移。
- 理由：文件管理资源真机截图和用户反馈证明 T7 的主轴铺满裁切会让初始比例过大、内容位于画布外并破坏点击映射。远控体验里底层分辨率固定不等于初始必须放大裁切。
- 影响：`X11ViewportPlan.fitLandscapeDesktop(...)` 初始 source rect 回到完整桌面，renderer zoom 回到 `100`；缩放后的 source rect 仍由手势相机和 native 回传维护。

## ADR-011 shell 桌面代理交接到 X11 后，shell 回调不得夺回 surface

- 日期：2026-07-02
- 决策：资源卡片继续使用 shell + `kite-open-desktop` 桌面代理；当 `/open-desktop` 已把同一 `CardRun` 实例更新为 `CardRunSurface.X11` 后，同一步 shell 的 progress/result 只补充运行绑定与报告文本，不再覆盖 surface 为 `Report`。
- 理由：文件管理资源的“闪退到 SH 报告”不是应用崩溃，而是同一运行实例的状态被 shell 回调覆盖。按照状态所有权规则，X11 handoff 成功后 surface 事实属于 X11 owner。
- 影响：不修改资源为 `type: x11`，不引入全局 X11 模式；修复点集中在 `handleShellProgress(...)` 与 `handleSequenceShellResult(...)`。

## ADR-012 PCManFM 小窗在资源启动层约束，不回退全局 X11 模式

- 日期：2026-07-02
- 决策：`kite.pcmanfm.x11` 打开时主动约束 PCManFM 自身窗口：启动前写 `~/.config/pcmanfm/default/pcmanfm.conf` 的 `win_width=1920`、`win_height=1080`，启动使用 `--new-win`，并用 `xdotool` 将窗口归位到 `0,0`、`1920x1080` 作为兜底。
- 理由：用户最新截图显示 X11 surface 已经存在，但 PCManFM 仍以 `640x480` 小窗出现；真机配置也证明当前实例保存了 `win_width=640`、`win_height=480`。这不是 Android 视口公式的根因，而是 X11 客户端窗口没有被资源启动脚本约束。
- 影响：底层 X11 仍固定 `1920x1080`，手机端缩放/平移继续只改变观察视口；不把文件管理资源切换为全局 X11 模式，不新增页面刷新，不修改指导文档。

## ADR-013 X11 后续线绑定 MEIZU 18 并与浏览器线物理隔离

- 日期：2026-07-04
- 决策：X11 后续长期任务使用物理目录 `D:\xm\Kite-x11-remote-control`、建议分支 `codex/x11-remote-control`、设备 MEIZU 18 `181QGEYH222B9`、host 转发端口 `18792`。
- 理由：用户明确要求浏览器线绑定一加，X11 线绑定魅族，并要求目录、构建任务和测试手机互不冲突。当前 `adb devices -l` 确认魅族 serial 为 `181QGEYH222B9`。
- 影响：X11 后续会话必须带 `adb -s 181QGEYH222B9`，不能复用浏览器线的一加设备或 `18791` host 端口。

## ADR-014 X11 竞品调研扩展为手机远控交互矩阵

- 日期：2026-07-04
- 决策：后续不只围绕“向日葵超级操作模式”这个单名词继续做，而是整理向日葵、ToDesk、TeamViewer、AnyDesk、RustDesk、Microsoft Remote Desktop 等手机版远控电脑的交互矩阵，再映射到 Kite X11。
- 理由：用户要求“研究透向日葵远程，或者很多其他远程软件手机版如何控制电脑”。现有 T1 已做向日葵初步资料，下一阶段需要系统化比较触控、鼠标、缩放、键盘、右键、滚轮、工具栏和错误反馈。
- 影响：后续实现任务要从矩阵中拆分，不一次性重写 X11；每个用户可见能力都要在魅族设备上截图或日志验证。
