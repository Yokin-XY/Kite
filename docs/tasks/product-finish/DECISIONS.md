# Kite 产品正式化决策记录

## ADR-PF001 设置中心是能力索引，不是全局事实 Store

日期：2026-07-20

决策：设置中心负责稳定分类、说明、类型化入口和轻量状态摘要。应用级偏好继续由 `SettingsGateway` 持有；终端、运行、资源、权限和诊断事实继续由现有拥有者持有。设置目录不得直接保存布尔值、运行状态、资源安装状态或权限结论。

理由：当前设置已经同时包含可写偏好和只读系统状态。如果把所有“看起来像设置”的能力继续并入一个 Snapshot，会复制状态、扩大刷新范围，并使设置页承担运行探测和平台副作用。

影响：新增能力先判断其属于全局偏好、功能默认值、系统权限、运行事实、实例参数还是实验/维护能力，再选择控制、状态摘要、导航、系统入口或动作类型。

## ADR-PF002 稳定分类固定，具体入口允许增长

日期：2026-07-20

决策：设置首页固定为“个性化、使用方式、系统、其他”四组，组内使用类型化二级入口。第一批二级页为外观与语言、应用行为、终端与工作台、浏览器与登录、权限与文件、运行环境、实验功能、帮助与关于。

理由：固定大类让新增能力有明确归属，同时避免首页随着功能数量增长成为超长卡片列表。用户按目的寻找设置，比按底层模块或技术名查找更稳定。

影响：以后新增普通设置优先进入已有二级页；只有出现新的用户目标且无法归入现有分类时，才新增顶层入口。

## ADR-PF003 版本号在发布门统一决定

日期：2026-07-20

决策：开发期间保持当前 `0.0.4`，不为每个内部里程碑修改或发布版本。设置中心、能力入口、真机验收和下一轮产品正式化共同通过后，以 `0.0.8` 作为候选正式版本；最终是否使用该版本在发布前依据实际范围确认。

理由：版本号应表达一组用户可感知且已经验收的产品变化，而不是每完成一段代码就机械递增。用户明确要求把多个更新合并进一个正式版本。

影响：当前任务不得提前修改 `versionCode/versionName`、创建 tag 或上传构建物。发布仍需单独的明确授权和完整 release gate。

## ADR-PF004 设置页面只做轻量绑定和显式校准

日期：2026-07-20

决策：设置页面只消费现有快照或持久化偏好 API；系统设置返回时显式刷新受影响状态。禁止在页面创建、绑定、滚动或周期计时器中执行文件、数据库、网络、运行时、工具链或 manifest 探测。

理由：设置中心会成为常用页面，若把隐藏诊断页的轮询或重型探测直接嵌入，会制造 UI 压力、ANR 风险和跨显示面副作用。

影响：旧 `StatusFragment` 和 `BridgeFragment` 只能作为功能迁移材料；正式入口必须改为按需动作或现有 Owner 的轻量投影，不能原样挂载。

## ADR-PF005 多来源目标使用上下文返回并保留安全回退

日期：2026-07-20

决策：运行管理这类可从首页状态面和设置二级页共同进入的目标，使用上下文返回；调用方可以登记准确返回动作，缺失上下文时仍回到首页安全父级。

理由：把运行管理固定为首页子页会破坏设置中的真实导航链；把它固定为设置子页又会破坏首页入口。上下文返回表达真实来源，不需要复制页面或增加入口特判。

影响：新增多来源目标时先复用 `BackPolicy.Contextual`，并明确 fallback；不能让目标页猜测来源，也不能依赖 Android Activity 历史偶然返回。

## ADR-PF006 终端主题从不可变标准色板生成

日期：2026-07-20

决策：终端明暗主题都从 Kite 自有的不可变标准色板生成，再写入 Termux 的当前默认色表；不得从可变的 `TerminalColors.COLOR_SCHEME` 反向捕获基础色。主题切换沿用现有会话颜色重置路径，不重连终端。

理由：Termux 暴露的是进程级可变色表。由 Fragment 首次读取它作为基准，会让创建顺序和此前主题影响下一次结果，无法稳定人工校准，也可能在多终端之间累计漂移。

影响：基础 ANSI 16 色可按明暗主题显式校准；扩展色保持标准索引语义，避免同一颜色作为背景时被单向对比度算法破坏。所有主题重复应用和切换必须具有确定性测试。

## ADR-PF007 快捷动作显式声明输入框副作用

日期：2026-07-20

决策：快捷动作注册项必须显式声明执行后保留还是清理实时预输入。Ctrl+C 作为中断动作清理输入框和同步缓冲；Enter 作为提交动作清理；Tab、Esc 和方向键等编辑/导航动作保留。不得再由发送字符串内容猜测动作语义。

理由：当前仅对回车字符串做清理，Ctrl+C 后仍保留已经实时写入 PTY 的输入文本，界面和 Shell 状态会分叉。字符串特判也无法承载以后新增动作的真实语义。

影响：操作注册表继续是扩展入口，但动作元数据增加类型化输入副作用；终端输入状态仍由现有 controller/Fragment 协作，不新增 Store，也不取消实时预输入。

## ADR-PF008 主题由统一环境解释，颜色与组件样式分层

日期：2026-07-20

决策：主题偏好继续由 `SettingsGateway` 持有，应用通过唯一的主题环境提供者把模式、颜色、样式键和系统状态解析成 `ThemeEnvironment`。颜色 token 与组件样式定义分层；样式通过注册表和类型化作用域扩展。页面只能消费环境，不得直接读取主题 SharedPreferences 或自行判断系统明暗。第一套 `standard` 样式保持当前结构与尺度，不在架构改造中决定最终品牌配色。

理由：统一不等于所有页面长得完全一样。统一的是入口、语义和继承关系；首页、资源、运行、终端等显示面仍可以在中央合同允许的范围内使用适合自己的组件变体。把颜色与样式混成几个页面分支，会让以后每换一套颜色或圆角都需要全局搜索和修改，也会再次造成应用外壳、系统栏和终端之间不一致。

影响：新增基础主题只需增加颜色定义；新增组件风格只需登记样式定义；局部差异通过 `ThemeScope` 解析，不在页面里用样式名写条件分支。终端现有明暗色板继续独立校准，但其“跟随”状态使用应用有效明暗；主题变化只更新外观消费者，不改变运行、资源、会话或 Web 状态。

## ADR-PF009 主题按语义和组件治理，不按页面名称扩展

日期：2026-07-20

决策：PF008 保留单一 `ThemeEnvironmentGateway`、有效明暗、语义颜色和特殊显示面边界；撤销“每个功能页通过 `ThemeScope` 获得长期样式覆盖”的扩展方向。主题分为可切换的颜色方案、可切换的组件配方、不可随主题切换的固定设计基础，以及有限跟随的独立内容。普通模块只组合标准组件和语义 token。

理由：统一读取只能解决当前分散，不能自动形成未来模块的接入标准。Material、Fluent、Carbon 和 Android Styles 的共同结构是原始值、语义、组件样式、组件、业务页面逐层消费；按首页、资源、设置继续增加作用域会把主题重新变成功能页特判。页面间距和触控尺寸虽然应该 token 化，也不等于应该随用户主题变化。

影响：当前 T014 不是推倒重做。Gateway、模式解析、消费者接线、系统栏和终端“跟随应用”继续使用；后续把页面级作用域收窄为组件变体、表面层级和特殊内容适配器，把 `ThemeComponentStyle` 拆成固定基础与组件配方，并将两个原始颜色升级成完整颜色方案。只有一套稳定风格时隐藏风格选择器。正式分类和新模块检查表以 `docs/architecture/theme-system.md` 为准。

## ADR-PF010 主题命令端与接收端通过中间规则协议解耦

日期：2026-07-20

决策：主题上游统一提交 `ThemeCommand`，持久化统一保存 `ThemeSelection`，注册能力由 `ThemeCatalog` 暴露，下游标准组件统一消费 `ThemeEnvironment`。`KiteTheme` 负责中央归一化、未知键回退和完整颜色解析；Android 系统状态、SharedPreferences 与 Bundle 留在各自适配层。页面级主题作用域和裸颜色命令不再是公共合同。

理由：设置端、未来命令端和接收组件若分别约定颜色整数、页面名称和样式字符串，任一侧改造都会迫使另一侧同步特判。中间协议把“用户想改什么”“长期保存什么”“组件最终得到什么”分开，两端可以独立演进。

影响：旧 `theme_color/background_color/theme_style` 仅作为迁移输入并转成受控自定义选择；新安装使用完整注册方案。首页和设置作为第一批组件配方样板，后续模块按语义组件接入。只有一套可选颜色方案或风格包时不显示临时选择器；终端、Web 和 X11 继续遵守各自内容适配策略。
